## 2. What actually happens when I run `mvnw spring-boot:run`

1. **Maven** reads `pom.xml`, resolves every declared dependency (Spring Boot
   starters, PostgreSQL driver, Hibernate, Thymeleaf, DevTools…) and puts
   them on the classpath.
2. Maven invokes the `spring-boot:run` goal, which launches
   `InternappApplication.main(...)`.
3. `SpringApplication.run(...)` starts a **Spring `ApplicationContext`** — a
   container that will hold every bean (controllers, services, repositories,
   the DataSource, etc.).
4. Because the main class is annotated with `@SpringBootApplication`, three
   things happen at once:
   - `@Configuration` — this class can define beans.
   - `@EnableAutoConfiguration` — Spring Boot inspects the classpath and
     auto‑wires sensible defaults. It sees `spring-boot-starter-webmvc` →
     starts embedded **Tomcat on port 8080**. It sees `spring-boot-starter-
     data-jpa` + `postgresql` driver → creates a **HikariCP** connection
     pool and a **Hibernate `EntityManagerFactory`**.
   - `@ComponentScan` — scans `com.example.internapp` and every sub‑package
     for `@Component`, `@Service`, `@Repository`, `@Controller`,
     `@RestController`, `@Configuration` and registers them as beans.
5. Spring Data JPA scans the `repository/` package, finds
   `UserRepository extends JpaRepository<User, Long>`, and creates a **proxy
   implementation at runtime** — I never write a single query, but I get
   `save`, `findAll`, `findById`, `deleteById` for free.
6. Hibernate reads `@Entity User`, sees `spring.jpa.hibernate.ddl-auto=update`,
   and issues `CREATE TABLE users (...)` if it does not yet exist.
7. Tomcat binds port 8080 and the log line
   `Started InternappApplication in ~3s` confirms the app is live.

That whole chain is what people mean by *"Spring Boot removes boilerplate."*
No `web.xml`, no `persistence.xml`, no manually constructing a `DataSource` —
it happens because a few JARs are on the classpath and I annotated one class.

## 3. Key annotations, in my own words

| Annotation | What it really does |
|---|---|
| `@SpringBootApplication` | The three‑in‑one entry point (config + auto‑config + component scan). |
| `@RestController` | Combines `@Controller` + `@ResponseBody`. Every method return value is serialized to JSON (via Jackson) and written straight to the HTTP response body — no view resolution. |
| `@Controller` | Marks a class as a web controller whose return values are **view names** (used by `HomeController` to return the Thymeleaf template `index`). |
| `@RequestMapping` / `@GetMapping` / `@PostMapping` / `@PutMapping` / `@DeleteMapping` | Map an HTTP verb + URL path to a Java method. Spring MVC's `DispatcherServlet` uses these to route incoming requests. |
| `@RequestBody` | Take the JSON in the request body and deserialize it into the annotated Java object. |
| `@PathVariable` | Extract a value from the URL (e.g. `/api/users/{id}` → `Long id`). |
| `@Valid` | Trigger Bean Validation on an incoming object. Any violation throws `MethodArgumentNotValidException`, which my `GlobalExceptionHandler` converts into a clean 400 JSON response. |
| `@Service` | Marks a class as a service‑layer bean. Functionally the same as `@Component`, but expresses *intent*. |
| `@Repository` | Marks a data‑access bean. Adds Spring's translation of native DB exceptions into `DataAccessException`. |
| `@Transactional` | Wrap the method (or every method of the class) in a database transaction. Commits on normal return, rolls back on runtime exception. I put it on `UserService` so each write is atomic. |
| `@Entity` + `@Table(name="users")` | Tells JPA "this class is a row in the `users` table." |
| `@Id` + `@GeneratedValue(strategy = IDENTITY)` | This field is the primary key; ask PostgreSQL to generate it (uses a `BIGINT GENERATED BY DEFAULT AS IDENTITY` column). |
| `@Column(unique=true, length=150)` | Fine‑tunes the schema Hibernate generates. |
| `@NotBlank`, `@Email`, `@Size(max=100)` | Jakarta Bean Validation constraints. Enforced when `@Valid` is present on the controller parameter. |
| `@Autowired` (constructor injection) | I actually rely on Spring's **implicit constructor injection**: when a class has a single constructor, Spring passes the required beans automatically — no `@Autowired` needed. This is the preferred style because it makes dependencies immutable, obvious, and testable. |
| `@RestControllerAdvice` | Global place for `@ExceptionHandler` methods; keeps error handling out of every controller. |

## 4. Why PostgreSQL, and how the connection is wired

**Why Postgres over an in‑memory DB (H2)?**

- The requirement asked for a *real* database, so bugs like schema mismatches,
  unique‑constraint violations, and connection‑pool exhaustion surface during
  development, not in production.
- Postgres is the de‑facto open‑source relational DB in industry — learning
  its behaviour (identity columns, `SERIAL`, transactions, `EXPLAIN`) is
  transferable.

**How the connection is configured (`application.properties`):**

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/intern_demo}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD:password}
spring.datasource.driver-class-name=org.postgresql.Driver
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.open-in-view=false
```

- **`${VAR:default}`** — read from an env variable, fall back to a default.
  This keeps real credentials out of Git; on any other machine you just set
  `DB_PASSWORD`.
- **HikariCP** is Spring Boot's default connection pool. Instead of opening a
  fresh TCP connection to Postgres for every request (slow), the pool keeps
  a handful of connections warm and hands them out.
- **`ddl-auto=update`** — on startup, Hibernate compares my `@Entity` classes
  to the live schema and issues `ALTER TABLE` statements to catch up. Great
  for development, dangerous for production (Flyway/Liquibase are safer
  there).
- **`open-in-view=false`** — disables the "OSIV" anti‑pattern that keeps a
  Hibernate session open for the whole HTTP request. Turning it off forces
  me to load exactly what I need inside the service layer.
- **`show-sql=true`** — logs every SQL statement, which is how I verified
  Hibernate was actually issuing `select u1_0.id, u1_0.email, u1_0.name
  from users u1_0` when the SPA polls `/api/users`.

## 5. The request → response flow (concrete example)

Say the browser calls `POST /api/users` with body `{"name":"Sam","email":"sam@x.com"}`.

```
Browser
   │  HTTP POST /api/users  { "name": "Sam", "email": "sam@x.com" }
   ▼
Tomcat  (embedded, port 8080)
   │  hands the raw request to Spring's DispatcherServlet
   ▼
DispatcherServlet
   │  looks up @RequestMapping ("/api/users" + POST) → UserApiController.create(...)
   │  Jackson deserializes the JSON body → new User(name, email)
   │  @Valid runs — @NotBlank/@Email pass, otherwise → GlobalExceptionHandler → 400
   ▼
UserApiController.create(user)
   │  calls userService.save(user)
   ▼
UserService.save(user)      ← wrapped in @Transactional
   │  calls userRepository.save(user)
   ▼
UserRepository (proxy)      ← generated by Spring Data JPA
   │  Hibernate: INSERT INTO users (name, email) VALUES (?, ?)
   │  Postgres assigns the identity id, returns it
   ▼
Hibernate populates user.id, returns the managed entity
   │  @Transactional commits the transaction, releases the pooled connection
   ▼
UserApiController.create(...)
   │  returns ResponseEntity.status(201).body(saved)
   ▼
DispatcherServlet
   │  Jackson serializes User → { "id": 7, "name": "Sam", "email": "sam@x.com" }
   ▼
Tomcat writes  201 Created  +  JSON body  → Browser
```

**If validation fails** (e.g. missing email), the `@Valid` step throws
`MethodArgumentNotValidException`. Because I registered a
`@RestControllerAdvice`, that exception never reaches Tomcat — my handler
converts it into `400 Bad Request` with a structured JSON body:

```json
{ "error": "Validation failed", "fields": { "email": "must not be blank" } }
```

The same advice class also turns duplicate‑email `DataIntegrityViolationException`
into `409 Conflict`, and my "not found" `IllegalArgumentException` into `404`.

## 6. MVC layering — *why* the extra classes?

I could have crammed everything into one controller. I didn't, because each
layer has a different responsibility:

- **Controller (`UserApiController`)** — knows HTTP. Parses request, calls
  the service, shapes the response. **No business logic here.**
- **Service (`UserService`)** — knows business rules. Enforces "user must
  exist before update", wraps operations in transactions. **No HTTP here** —
  I could reuse this service from a scheduled job or a CLI.
- **Repository (`UserRepository`)** — knows the database. Since it extends
  `JpaRepository`, Spring generates the implementation. If I ever need a
  custom query, I add a method like `findByEmail(String email)` and Spring
  Data derives the SQL from the method name.
- **Entity (`User`)** — knows the shape of a row.

That separation is what makes the code **testable** (I can unit‑test the
service with a mock repository and no database) and **replaceable** (swap
Postgres for MySQL by changing two properties — no service code changes).

## 7. Things I learned by breaking stuff

- **Boot 4.x renamed `spring-boot-starter-web` → `spring-boot-starter-webmvc`.**
  I found this by getting a "starter not found" error and reading the release
  notes.
- **`@GeneratedValue(strategy = AUTO)` sometimes tries to create a hibernate
  sequence** on Postgres 10+. Explicitly using `IDENTITY` avoided that.
- **Port 8080 collisions** — if a previous `mvnw` run didn't shut down
  cleanly, the next run fails with `Address already in use`. Fixed with
  `Get-Process java | Stop-Process -Force` on Windows.
- **Hardcoding the DB password in `application.properties` is a leak
  waiting to happen** on a public repo. Switching to `${DB_PASSWORD:...}`
  reads from an env var and only falls back for local dev.
- **`open-in-view=true` (Spring's default) is convenient but hides lazy‑load
  performance bugs.** I turned it off and would rather see a
  `LazyInitializationException` at dev time than in production.
- **Spring Boot DevTools** watches `target/classes` (not source). Editing an
  HTML template auto‑reloads instantly; editing a Java file needs a compile
  first (IDE auto‑build, or `mvn compile` in another terminal).

## 8. What I built *beyond* the checklist (and why)

The task only required a Hello endpoint + a `User` entity + a repository.
I went further because the mentor's note said "understand, don't copy‑paste":

- **Full CRUD REST API** (`GET/POST/PUT/DELETE /api/users`) — to actually
  exercise the repository, not just prove it compiles.
- **`GlobalExceptionHandler`** — to see how Spring MVC's exception pipeline
  works and to return clean JSON errors instead of stack‑trace HTML pages.
- **SPA UI** (Thymeleaf shell + vanilla JS + Bootstrap) — so I could
  observe the request/response cycle live in the browser DevTools tab.
- **DevTools** — to feel the difference between a cold restart and hot
  reload, and to learn what a two‑classloader restart actually is.
- **README + screenshots + this SUMMARY.md** — because a project I can't
  explain is a project I don't understand.

## 9. Open questions I want to explore next

1. **Migrations.** `ddl-auto=update` is fine for me alone, but on a team
   two people editing the schema at once would collide. When do I switch
   to Flyway or Liquibase, and how does it fit into CI/CD?
2. **Testing.** I have the `spring-boot-starter-test` deps on the
   classpath but only the default context‑loads test. What does a good
   `@DataJpaTest` (repository slice) and `@WebMvcTest` (controller slice)
   look like, and how do they differ from full `@SpringBootTest`?
3. **DTOs vs entities on the wire.** Right now I return the `User` entity
   straight from the controller. That works today, but the moment I add a
   `password` field it leaks. I want to learn record‑based DTOs
   (`UserResponse`, `UserCreateRequest`) and MapStruct.
4. **Authentication.** No auth today. Next step is Spring Security with
   JWT so the API is not wide open.
5. **Observability.** Actuator, Micrometer, `/actuator/health` and
   `/actuator/metrics` — how do teams monitor a Spring Boot app in prod?

## 10. TL;DR

Spring Boot is not magic — it is a *conventions engine*. Annotations
declare intent, the classpath tells Boot which auto‑configurations to
activate, and everything else is beans wired into an application context.
Data JPA generates the repository implementation, Hibernate translates my
entity into SQL, HikariCP recycles Postgres connections, and Tomcat serves
the HTTP layer. My job is to **layer responsibilities cleanly** — HTTP in
controllers, rules in services, persistence in repositories — so that any
of those pieces can be swapped, tested, or extended without rewriting the
rest.
